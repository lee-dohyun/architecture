# 사용자 설명서 표준 양식

PosSelect 의 화면을 **쓰는 사람**(파트너·직원·고객)을 위한 설명서를 쓰는 규칙과 양식이다.
코드 주석([COMMENT_STANDARDS.md](COMMENT_STANDARDS.md))·ADR·인시던트 위키는 개발자용이고, 이 문서는 그것들과 독자가 다르다.

> 도입: lee-dohyun/architecture#30 (2026-09-29). 첫 적용 사례는 아래 "예시" 참고.

## 1. 언제 쓰나 — 규칙

1. **사용자에게 보이는 동작이 바뀌면 같은 PR 에서 설명서도 고친다.** 새 화면, 입력 항목·검증 규칙 변경,
   상태 흐름 변경, 사용자에게 보이는 메시지 변경이 모두 해당한다. 내부 리팩터링·성능 개선만이면 필요 없다.
2. 위치: **그 화면을 가진 저장소의 `docs/user-guide/<업무>.md`**. 코드와 같은 곳에 둬야 같은 PR 에서 같이 리뷰된다.
3. 파일 하나 = **사용자의 업무 하나**(예: "상품 등록하고 검수 받기"). 화면 단위가 아니다 — 사용자는 화면이 아니라 일을 하러 온다.
4. 설명서가 없는 기존 기능을 고칠 때는 그 기회에 새로 만든다(전체 소급은 하지 않는다).

## 2. 어떻게 쓰나 — 작성 원칙

| 원칙 | 이유 |
|---|---|
| 독자는 **개발 용어를 모른다.** `DRAFT`, `401`, `BFF`, `토큰` 대신 화면에 보이는 말을 쓴다 | 파트너는 회사 밖 사람이다 |
| 화면에 보이는 **버튼·메뉴·메시지는 원문 그대로** `「」` 로 인용한다 | 사용자는 화면 글자로 찾는다. 바꿔 쓰면 못 찾는다 |
| 메시지 원문은 **코드에서 복사**한다(기억·추측 금지) | 메시지를 고치면 설명서도 틀린다 — 그래서 1-1 규칙이 있다 |
| "최종 확인"에는 **실제로 화면을 돌려 본 날짜와 배포 커밋**을 적는다 | 코드만 읽고 쓴 설명서는 틀려도 아무도 모른다 |
| 확인하지 못한 동작은 쓰지 않거나 `(미확인)` 으로 표시한다 | 틀린 설명서는 없는 것보다 나쁘다 |
| 절차는 **번호 목록**, 한 단계에 행동 하나, 각 단계 끝에 **결과(무엇이 보이면 성공인지)** | "됐는지"를 사용자가 스스로 판단하게 |
| 제약·금지 사항은 **이유와 함께** 쓴다 | 이유를 모르면 우회하려 든다 |
| 스크린샷은 선택. 넣으면 `docs/user-guide/img/` 에 두고 화면이 바뀌면 같이 교체 | 낡은 스크린샷은 틀린 설명이 된다 |

## 3. 템플릿

아래를 `docs/user-guide/<업무>.md` 로 복사해서 채운다. 해당 없는 절은 지우지 말고 "해당 없음"이라고 쓴다
(빠뜨린 건지 없는 건지 구별하기 위해서다).

````markdown
# <업무 이름> 사용 설명서

| 항목 | 내용 |
|---|---|
| 대상 | <누가 쓰나: 판매 파트너 / 상품 담당 직원 / 고객 …> |
| 화면 주소 | <https://…> |
| 필요한 권한 | <계정 종류·역할. 없으면 "로그인만"> |
| 최종 확인 | <YYYY-MM-DD, 배포 커밋 `abc1234` 에서 실제 화면으로 확인> |
| 관련 이슈 | <owner/repo#번호> |

## 1. 이 기능으로 할 수 있는 일
<3줄 이내. 사용자의 말로.>

## 2. 시작하기 전에
- <계정은 어떻게 받나 / 미리 준비할 것(사진, 서류, 정보)>

## 3. 따라 하기
### 3-1. <작업 이름>
1. <행동> → <결과: 무엇이 보이면 성공>
2. …

## 4. 입력 항목 설명
| 항목 | 필수 | 설명 | 입력 규칙 |
|---|---|---|---|
| | | | |

## 5. 상태와 진행 흐름
| 상태(화면 표시) | 뜻 | 다음에 할 일 / 누가 |
|---|---|---|
| | | |

## 6. 자주 보는 메시지와 해결 방법
| 화면 메시지(원문) | 원인 | 해결 |
|---|---|---|
| | | |

## 7. 알아 둘 제한 사항
- <제약> — <이유>

## 8. 문의

## 변경 이력
| 날짜 | 변경 | 이슈 |

````

## 4. 리뷰 체크리스트 (PR 리뷰어용)

- [ ] 사용자에게 보이는 변경인데 `docs/user-guide/` 가 안 바뀌었으면 요청한다
- [ ] 메시지 원문이 코드와 글자까지 같은가
- [ ] "최종 확인"이 이번 변경 이후 날짜·커밋인가
- [ ] 개발 용어(상태 코드, enum 이름, API 경로)가 본문에 새어 나오지 않았나
